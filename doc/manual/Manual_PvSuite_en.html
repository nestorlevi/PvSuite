          01What PV Suite is

          PV Suite is a set of tools to build supervision systems (HMI / SCADA) based on pvbrowser. It works like a web browser, but for industrial applications:

          ComponentWhat it does
          pvserverThe program you write (in C++, or Lua / Python). It defines the screens ("masks") and the logic: what is shown, what happens when a button is pressed. It runs on the server.
          pvbrowserThe client. It connects to a pvserver (port 5050 by default) and shows its screens. Several PCs can connect to the same pvserver.
          pvdevelopThe development environment: code editor, graphical screen designer (Designer), compilation and daemon configuration.
          daemonsPrograms that talk to the PLCs (Modbus, Siemens S7, ...) and put the data in a shared memory. The pvserver reads it from there and sends the writes through a mailbox.
          rllibLibrary with the classes for daemons, shared memory, sockets, threads, files, etc.
           PLC ──(Modbus / S7)──> daemon ──> shared memory ──> pvserver ──(network)──> pvbrowser
                                   ^                             │
                                   └────────── mailbox ──────────┘   (writes)

          Separating the communication (daemon) from the interface (pvserver) means that a communication failure does not block the screens and that several pvservers can use the same data.

          02Installation

          2.1Windows

          Run PvSuite-<version>-Setup-win64.exe (download it from github.com/nestorlevi/PvSuite/releases). The installer has these components:

          ComponentContentFolder
          pvbrowser (client)pvbrowser with web browser (Qt WebEngine). It is all a PC that only connects to pvservers needs.<target>\win-msvc\bin
          Development suite (pvdevelop)pvdevelop, rllib tools, libraries to compile pvservers (MinGW and Visual Studio), documentation and examples.<target>\win-mingw\bin
          Libraries for MinGW 8.1 (Qt 5.15) (optional)librllib and libserverlib built with MinGW 8.1 for 64 bits (mingw81_64) and 32 bits (mingw81_32), to keep building older projects (Qt 5, 32 or 64 bits) with MinGW 8.1 and Qt 5.15.2, and then move them to the Qt 6 MinGW. It does not include the compiler or Qt: they are installed with the Qt installer.<target>\win-mingw\bin\mingw81_64, mingw81_32
          Common filesDocumentation, examples and headers of pvserver and rllib.<target>\doc, ejemplos

          On a PC that only connects to pvservers (operator station) the development suite can be unchecked. The default target is C:\PVSuite. The installer creates the variable SUITEDIR, adds win-mingw\bin to the user's PATH and creates shortcuts to pvdevelop and pvbrowser.

          Each folder has its own Qt: pvbrowser uses the Visual Studio one (because of Qt WebEngine) and pvdevelop the MinGW one. That is why they are in separate folders; do not mix their files.

          Help > Check for updates (pvdevelop and pvbrowser) looks up the latest version published on GitHub (github.com/nestorlevi/PvSuite/releases) and offers to download the installer. pvdevelop also checks once a week at start-up (it can be switched off in the same menu).

          Compiler for the projects

          A compiler is needed to build the pvservers (not to use pvbrowser, nor for pvservers in Lua):

          • MinGW (default): the one of Qt 6.9, C:\Qt\Tools\mingw1310_64 (installed with the Qt installer).
          • Visual Studio 2022 (optional): Build Tools or Community.
          • MinGW 8.1 with Qt 5.15.2 (optional, for older projects): 64 bits C:\Qt\Tools\mingw810_64 and C:\Qt\5.15.2\mingw81_64; 32 bits C:\Qt\Tools\mingw810_32 and C:\Qt\5.15.2\mingw81_32. Check the component "Libraries for MinGW 8.1" when installing and choose that MinGW in pvdevelop. The project's .pro picks the libraries by itself (mingw81_64 or mingw81_32) according to the compiler, with one more line (equals(QMAKE_GCC_MAJOR_VERSION, 8):contains(QT_ARCH, i386):PVB_MINGWLIB = $(PVBDIR)/win-mingw/bin/mingw81_32), which pvdevelop adds by itself to projects that already had the mingw81_64 one. When the MinGW is changed (for example from GCC 13 to MinGW 8.1 32 bits), pvb_build.bat deletes the leftovers of the previous build (.qmake.stash, the Makefile.win*, the .o files and the project's .exe) and builds again.
          • If the pvserver uses Qt (for example QT += sql), also the Qt kit of the same compiler (C:\Qt\6.9.2\mingw_64 or msvc2022_64).

          The folders are set in pvdevelop: Action > Compiler... (see chapter 6).

          2.2Linux

          The installer PvSuite-<version>-Setup-linux-x64.run (chmod +x and run it) installs into /opt/pvb with links in /usr/bin and /usr/lib. "Bundled Qt libraries" can be unchecked to use the system's Qt 6 (with Qt WebEngine). If desktop libraries are missing (xcb, WebEngine) the installer says so: sudo sh /opt/pvb/terceros/preparar_linux.sh installs them (apt, dnf or zypper). The pvservers are built with g++ and make: sudo sh /opt/pvb/terceros/preparar_linux.sh -compilar.

          03pvdevelop: the development environment

          On Windows it is opened with the pvdevelop6 shortcut (it runs start_pvdevelop.bat, which prepares the environment). On Linux with pvdevelop.

          3.1Creating a project

          1. File > New pvserver (Ctrl+N): choose an empty folder and the name (for example pvs).
          2. pvdevelop generates the project:
            FilePurpose
            pvs.proqmake project (libraries, files).
            main.cppStart of the pvserver and choice of the initial mask.
            pvapp.hCommon declarations (include the daemons' .h files here).
            mask1.cppScreen 1, generated by the Designer. Do not edit by hand.
            mask1_slots.hLogic of screen 1: this is where you program.
          3. Action > Insert Mask (Ctrl+I) adds more screens.

          3.2Views and toolbars

          ShortcutAction
          Ctrl+ECode editor
          Ctrl+DDesigner (screen layout)
          Ctrl+MCompile the project
          Ctrl+TRun the pvserver
          Ctrl+POpen pvbrowser (connected to the pvserver)
          Ctrl+F / Ctrl+RFind / Replace
          Ctrl+S, Ctrl+BSave, backup
          Ctrl+H / F1Manual / help of the current window
          Ctrl+JShow or hide the build console

          In the editor the Compilation toolbar (compiler of the projects) is shown, and in the Designer the Align toolbar (align widgets). Each toolbar is only shown in its view.

          3.3Code completion

          While typing in the editor, suggestions appear (pvserver functions, words of the project). They are accepted with Enter or Tab; Ctrl+Space shows them on request. It is switched off in Action > Compiler...

          3.4Language

          pvdevelop and pvbrowser are available in English, Spanish, Portuguese and German. By default they use the system language (English if it is none of those). To choose another one: in pvdevelop the Language menu, in pvbrowser File > Language. The change applies the next time the program is started. The installer also uses the system language.

          The translations are Qt Linguist files that can be edited or extended: pvdevelop/translations/pvdevelop_xx.ts and pvbrowser/translations/pvbrowser_xx.ts (open them with linguist; they are built into the program when compiling). This manual is also available as Manual_PvSuite (Spanish), _pt and _de.

          3.5Build console

          Ctrl+M, Ctrl+T and the Compile button of the daemons compile in a panel at the bottom of pvdevelop, without extra windows (Action > Build console or Ctrl+J shows or hides it; it can be moved or undocked). Errors are shown in red and warnings in orange; double-clicking an error opens the file at that line, and in the editor the lines with errors are marked (hover to see the message). Ctrl+T, if the build succeeded, runs the pvserver. On Linux it opens in a window of the system terminal (x-terminal-emulator, qterminal, konsole, gnome-terminal, xfce4-terminal, lxterminal, mate-terminal or xterm) that is closed like any window; Ctrl+T first closes the previous pvserver of the project. Without a terminal it runs inside the build panel and the Stop button closes it. Predictive text also suggests the widget names of the masks and the daemons' tags (PLC1_Motor1, PLC1_SYS...).

          The console is enlarged or shrunk by dragging its border or with the arrows of its bar, and the two-windows button detaches it into a separate window. In the predictive text list an icon tells what each word is: W widget, T tag, D daemon, f pvserver function, C rllib class. Action > Insert function includes the tags (with a daemon and a tag name of the project) and the system tags.

          3.6Document tabs

          A tab bar sits above the work area: each tab shows a screen in the Designer or a file in the editor. Whatever is opened from the screen list, the editor buttons or the Designer's Screen combo replaces the document of the current tab. To keep it open and look at another one, use a new tab:

          • + (right of the tabs): picks another project file and opens it in a new tab.
          • Right-click on a screen in the list: Open in new tab (Designer) or Open maskN_slots.h in new tab. If it is already open, that tab is selected.
          • Tabs are reordered by dragging. An orange dot instead of the X means unsaved changes; Save all saves every modified tab.
          • Each editor tab keeps its own Ctrl+Z history: going back to a tab continues undoing what was typed there, not another file.
          • If a file disappears from the disk, its tab closes and the status bar says so.

          3.7Indentation and code formatting

          Action > Compiler... has the Indentation setting: 2, 3, 4 or 8 spaces per level, or tab. It is used by:

          • Tab inserts one level. With several lines selected it adds one level to every line that has text; Shift+Tab removes one level (on a line or on the selection).
          • Enter after { indents the next line.
          • Right-click > Format code (selected lines or the whole file): re-indents according to the C/C++ braces { }. It leaves preprocessor lines (#), /* */ comments and continuations of a statement with an open parenthesis as they are. After if, for, while or else without a brace, the next line gets one more level.

          Tabs already present in a file are shown with the same width as the chosen level (with tab: 4).

          04The Designer: drawing screens

          4.1Inserting widgets

          • Double click on an empty place, or Shift+click: opens Insert widget (buttons, labels, images, tables, plots, TextBrowser, ...). For images there is a button to choose the file.
          • Ctrl+Shift+click: inserts the last widget type again.
          • Each widget has a name (objectName). The code uses it by that name: pvSetText(p, Title, "Hello").

          4.2Selecting, moving and properties

          • Dragging the mouse over an empty area selects several widgets. Ctrl+click adds or removes one.
          • Arrows move; Ctrl+arrows resize. Ctrl+Z undoes the last move.
          • P or Alt+click: widget properties. Del: deletes.

          4.3Aligning

          With several widgets selected, the Align toolbar aligns them left, right, top or bottom (the first selected one is the reference) and distributes the horizontal or vertical space between the outer ones.

          4.4Copy and paste

          Ctrl+C / Ctrl+V copy the selected widgets of any type, including the contents of containers (for example a Frame with everything inside it). When pasting, each copy keeps its name with a number: Motor → Motor_1, Motor_2.

          05Programming a pvserver

          5.1The slots

          Each screen has functions in maskN_slots.h that are called on each event:

          SlotWhen it is called
          slotInit(p, d)When the screen opens: initial values, downloading images.
          slotNullEvent(p, d)Periodically (every 1 s by default, -sleep=500 on the command line): update the process values.
          slotButtonEvent(p, id, d)Click on a button (also Pressed and Released).
          slotTextEvent(p, id, d, text)A text changed (LineEdit) or a TextBrowser navigated.
          slotSliderEvent(p, id, d, val)A slider, dial or spinbox moved.
          slotCheckboxEvent, slotRadioButtonEventCheck boxes and radio buttons.
          slotTableTextEvent, slotTableClickedEventTables.
          slotMouse...Event, slotKeyboardEventMouse and keyboard (SVG drawings, plots).

          The id parameter is the widget name; p identifies the client connection; d is the screen data.

          5.2Screen data: DATA

          Each screen has its own DATA structure (one per connected client). pvdevelop generates it inside a namespace { }, so every mask has its own even if they have functions with the same name:

          namespace { // DATA propia de esta mascara (own DATA of this mask)
typedef struct
{
  int counter;
  int mode() { return counter % 2; }
}
DATA;
} // namespace
          In old projects, if two masks have functions inside DATA, add the namespace { } by hand. Without it the linker may use the function of another mask (with MSVC the pvserver crashes).

          5.3Examples

          Showing a value and changing the colour

          static int slotNullEvent(PARAM *p, DATA *d)
{
  float t = readTemperature();
  pvPrintf(p, LabelTemp, "%.1f °C", t);
  if(t > 80) pvSetPaletteBackgroundColor(p, LabelTemp, 255, 0, 0);  // red
  else       pvSetPaletteBackgroundColor(p, LabelTemp, 0, 200, 0);  // green
  return 0;
}

          A button that changes the screen

          static int slotButtonEvent(PARAM *p, int id, DATA *d)
{
  if(id == ButtonAlarms) return 2;   // number of the mask to show
  return 0;
}

          Images and files

          static int slotInit(PARAM *p, DATA *d)
{
  pvDownloadFile(p, "Images/background.png");  // the client stores it in its temporary folder
  pvSetImage(p, Background, "background.png");
  return 0;
}
          Relative paths are searched in the folder the pvserver is run from. Run it from the project folder (pvdevelop already does), not from release.

          Confirmation message

          // type: BoxInformation, BoxWarning or BoxCritical
pvMessageBox(p, ButtonStop, BoxWarning, "Stop the pump?", MessageBoxYes, MessageBoxNo, 0);
// the answer arrives at slotSliderEvent(p, ButtonStop, d, val) with val = MessageBoxYes or MessageBoxNo

          The complete list of functions is in the programming reference (doc/pvslib).

          The Compilation toolbar (Editor view) has the MinGW / MSVC selector. A compiler that is not found in the configured folder is disabled. The folders, the number of processors and code completion are configured in Action > Compiler...:

          FieldExample

          Qt for MinGW (optional)C:\Qt\6.9.2\mingw_64

          6.2Compiling and testing

          1. Ctrl+M compiles. Errors appear in the compilation window.
          2. Ctrl+T runs the pvserver (port 5050).
          3. Ctrl+P opens pvbrowser connected to localhost.

          If the project uses Qt (QT += sql, core, ...) the Qt kit of the compiler must be configured; otherwise the compiler is enough.

          6.3The .pro file

          pvdevelop adds blocks for MinGW (win32-g++) and Visual Studio (win32-msvc*). If Windows functions that are not in the default MSVC libraries are used (for example ShellExecute), add in the win32-msvc* block:

          LIBS += -lshell32

          07pvbrowser: the client

          Type the address of the pvserver in the bar (for example 192.168.1.10 or pv://192.168.1.10:5050) and press Enter. The options (full screen, zoom, temporary folder) are in the menu; the language in File > Language.

          7.1Web pages and Grafana

          The TextBrowser widget is a complete browser (Qt WebEngine): it shows web pages, HTML with JavaScript and Grafana dashboards. In the pvserver:

          pvSetSource(p, Browser, "https://www.example.com");          // a page
pvDownloadFile(p, "Help/manual.html");                         // a file of the project
pvSetSource(p, Browser, "manual.html");
pvSetText(p, Browser, "<h1>Status</h1><p>All OK</p>");     // generated HTML

          An embedded Grafana panel (in grafana.ini: allow_embedding=true and read-only anonymous access):

          pvSetSource(p, Chart,
  "http://192.168.1.10:3000/d-solo/abc123/plant?orgId=1&panelId=2&refresh=5s&theme=light");

          Grafana is good for history and analysis; for real-time values the pvbrowser plots (Qwt) are better.

          08PLC communication: daemons

          The daemons are configured from the Daemon menu of pvdevelop: Modbus, Siemens TCP, PPI. Each one has a configuration file (.mkmodbus, .mksiemens). The Compile button generates the daemon (C++) and the .h used by the pvserver, and compiles it.

          A new file keeps the shared memory and the mailbox in the project's automation folder, with a relative path: shared_memory=automation/shm/PLC1.shm and mailbox=automation/mbx/PLC1.mbx. So the project can be moved to another folder or PC without changing anything. The programs run from the project folder (pvdevelop and the shortcuts do it by themselves); the folders are created automatically. \, \\ or / are accepted (on Linux, /). On Windows the mailbox name is valid for the whole PC: two projects with a daemon of the same name cannot run at the same time. If a daemon file already has tags, opening it also opens the tag editor; when it is closed the daemon window remains to compile.

          8.1Modbus: configuration

          shared_memory=c:\automation\shm\plc1.shm
mailbox=c:\automation\mbx\plc1.mbx
communication=socket          # socket (Modbus TCP) or serial (RTU / ASCII)
tcpadr=192.168.1.20
tcpport=502
#tty=COM1  baudrate=9600  parity=0  protocol=0

          8.2The classic way: cycles

          It can still be used as before: each cycle reads a fixed block of registers.

          cycle1 slave=1 function=3 start_adr=0 num_register=50

          In the pvserver it is read by position: PLC1.readShort(PLC1_CYCLE1_BASE, 49). Existing projects work without changes. The recommended way now are tags (next chapter): they can be combined with cycles in the same file.

          8.3Compiling the daemon

          Compile generates the code and compiles it in its own window (like Ctrl+M), with MinGW or Visual Studio depending on the selected compiler: pvdevelop is not blocked while it compiles. If the daemon is running, the window asks whether to close it (its .exe cannot be replaced while it runs). Close saves the file and compiles only if it changed since the last compilation (or if the .exe is missing). On Windows this is done by win-mingw\bin\pvb_make_daemon.bat name [ppi]; on Linux, by an xterm window.

          8.4Console messages

          The daemon numbers its cycles. In the tag editor, Daemon console selects what it writes in its window (console= in the file):

          LevelWhat it shows
          Quiet (quiet, -q)Errors only: when a block can no longer be read and when it comes back, and write errors.
          Normal (normal, -n)The same plus a summary every console_interval seconds (10).
          Verbose (verbose, -v)Every block read with the cycle number, slave, address, result and how long it took; and the end of every cycle.
          [ciclo 1234] bloque 2/5 esclavo 1 FC3 40300..40301 ok 1 ms
[ciclo 1234] fin: bloques ok=5 error=0, 3 ms
[ciclo 1300] 66 ciclos en 10 s, ultimo 1 ms (max 12), bloques ok=5 error=0, errores lectura=0 (0 nuevos) escritura=0

          When running the daemon, -q, -n or -v change the level without compiling again.

          8.5System tags

          The Modbus and Siemens daemons write the communication status at the end of the shared memory. pvdevelop adds them to the .h as PLC1_SYS:

          TagTypeMeaning
          ComunicacionboolAll blocks of the last cycle were read correctly
          ComunicacionParcialboolSome blocks were read correctly and some failed
          ConectadoboolConnection open (socket or serial port)
          BloquesOk, BloquesErroruintResult of the last cycle
          CicloudintCycle number
          TiempoCiclo, TiempoCicloMaxudintDuration of the last cycle and the maximum, in ms
          ErroresLectura, ErroresEscrituraudintRead and write error counters since the daemon started
          UltimoErrordintCode of the last error (0 = none)
          UltimaLecturaOk, InicioudintTime of the last correct read and of the start (seconds since 1970, UTC)
          Esclavo<n> / Plc<n>boolModbus slave or S7 PLC n answered in the last cycle
          if(!PLC1.getBool(PLC1_SYS.Comunicacion)) pvSetText(p, lbStatus, "No communication");
if(!PLC1.daemonAlive(PLC1_SYS.Ciclo))     pvSetText(p, lbStatus, "The daemon is not running");
int ms = PLC1.getInt(PLC1_SYS.TiempoCiclo);

          daemonAlive(tag, seconds) (5 by default) tells whether Ciclo advanced during those seconds: if the daemon stops, the other tags keep their last value. Without prefix: SYS.Comunicacion (with using namespace tags_PLC1;).

          The system tags go after the cycles and the tags: the shared memory grows, and the daemon and the pvserver are compiled with the same .h, as always.

          8.6Simulation

          To test with a simulator without changing the IP or recompiling, in the same .mkmodbus:

          tcpadr=192.168.1.20               # the PLC
simulation_tcpadr=127.0.0.1       # the simulator
simulation_tcpport=502

          The daemon started with -sim (or with the environment variable PVB_SIMULATION=1) connects to the simulator; otherwise, to the PLC. The tags, the shared memory and the .h are the same, so the pvserver does not change. It also works with a serial (RTU) daemon: in simulation it uses Modbus TCP. A second file (PLC1_Simulacion.mkmodbus) with other tag names is no longer needed. Daemon > Modbus loads the first .mkmodbus of the project folder (Open chooses another one).

          8.7Tag monitor

          Daemon > Tag monitor... shows live the value and quality of the tags of each daemon (it reads the .tagmap files and the shared memory, read only), with a name filter: useful for debugging without touching the pvserver. The Start daemon and Start in simulation buttons run it in its own window, normally or with -sim.

          It is also available as an icon on the Project toolbar, in the Designer and in the editor. At the top you choose the Daemon (a .tagmap from the project folder) and the Filter; Pause freezes the table. Columns: Tag, Value, Quality, Forced, Type, Description (click on a title to sort). Quality is good, error or stopped: if SYS.Ciclo does not advance for 5 seconds the monitor warns in red DAEMON STOPPED and the values are the last ones the daemon left.

          Writing and forcing values

          Choose a tag from the list, type the Value and use:

          ButtonWhat it does
          WriteWrites the value once (the PLC may change it afterwards).
          ForceWrites the value again every time it changes (at most once per second) until Release or until the monitor is closed. The row turns yellow and the Forced column shows it.
          Release / Release allStops forcing the chosen tag or all of them.

          Only rw=1 tags can be written. The first time in each session it asks for confirmation, because with the real daemon (no simulation) you are writing to the machine. Write and Force are only enabled if the daemon was compiled with this version of pvdevelop (the .tagmap carries mailbox= and the addresses); otherwise the status line says so: compile the daemon again. Writes go through the daemon's mailbox, like those of the pvserver.

          09Tags: named variables

          A tag is a PLC variable with a name, an address and a type. pvdevelop groups contiguous or nearby addresses into blocks and the daemon reads each block in a single request (like commercial SCADA systems).

          9.1Tag editor

          In the daemon window, Tags... button. The Variables tab has the tag table and the settings; the Structures tab defines compound types (chapter 10). The Check button shows the read blocks. The variables can be saved in the daemon file or in a CSV (editable with Excel); Import/Export CSV is also available.

          The Daemon selector at the top lists the daemons of the same protocol in the project folder: when you choose another one, the editor asks whether to save the changes and opens that daemon's tags without going through its window.

          9.2Address notation (Modbus)

          NotationHolding registerRegister bitInput registerCoilDiscrete input
          Modicon (base 1)4000140300.15300010000110001
          Offset (base 0)HR0HR299.15IR0CO0DI0
          PLC (Schneider)%MW0 (%MD, %MF 32 bit)%MW299.15%IW0%M0%I0

          When the notation is changed in the editor, the addresses of the table are converted automatically.

          9.3Columns

          ColumnMeaning
          NameLetters, digits and _. It is the name in the code: PLC1_<name>.
          Typebool, int (16 bit), uint, dint (32), udint, real, lreal, byte (S7) or a structure. (auto): from the address.
          Count / StrideArrays (chapter 10).
          RWCan be written from the pvserver.
          SlaveModbus slave number (or PLC number in S7).
          ScanMilliseconds between reads; 0 = every daemon cycle. Slow variables with a large scan reduce the network load.
          Scale / Offsetvalue = raw × scale + offset (in getReal and setReal).
          OrderWord order of 32-bit values: ABCD (standard), CDAB (swapped words, very common), BADC, DCBA.

          9.4Writing bits

          A bit of a holding register (40300.15) can be written in two ways (setting Bit writing):

          • Read-modify-write (default): the daemon reads the register, changes the bit and writes it. Works with any PLC.
          • Function 22 (Mask Write Register): the PLC changes the bit. Only if the PLC supports it.

          9.5In the .mkmodbus file

          address_notation=modicon
word_order=CDAB
bit_write=rmw
tag name=FlagTWR address=40300.15 rw=1 desc="Control from tower"
tag name=Flow    address=40311 type=real rw=1
tag name=Temp    address=30011 type=int scale=0.1
tag name=Slow    address=40500 type=int scan=1000
tags=PLC1_tags.csv            # optional: more tags in a CSV

          CSV columns: name;address;type;count;stride;rw;slave;scan;scale;offset;order;description

          9.6How the daemon reads

          Cycles and tags together

          cycle and tag lines are used at the same time. In each loop the daemon:

          1. reads the cycles, in order (their data goes at the beginning of the shared memory, PLC1_CYCLE1_BASE, ...);
          2. updates the life counter and the error counters;
          3. reads the tag blocks (those with a scan only when it is their turn);
          4. waits, if needed, so that the loop lasts at least cycletime ms.

          Without tags the daemon works as before (it produces the same shared memory). If only tags are used, it is better to delete the cycles: the template has example cycles for slaves 1 to 7, and a slave that does not exist makes the daemon wait for the response timeout in every loop, which also slows down the tag reading. If cycles and tags read the same registers, they are read twice (it works, but it is extra traffic).

          Scale and Offset

          value = raw × Scale + Offset. It is applied in getReal() and, reversed, in setReal(); getInt() returns the raw value. Examples:

          The PLC sendsScaleOffsetResult
          Tenths of a degree (253)0.1025.3
          0 to 27648 for −50 to 150 °C0.0072338−5027648 → 150
          Thousandths of a bar0.00101500 → 1.5

          Scan and grouping

          Two tags are read in the same request only if they have the same slave, area (holding, input, coil, discrete; in S7 the area and the DB number) and scan. Contiguous tags with a different scan go in separate requests, each one at its own rate:

          tag name=A address=%MW0              # scan 0
tag name=B address=%MW1              # scan 0     -> A and B: one request in every loop
tag name=C address=%MW2 scan=1000    # another request, every 1 s

          The scan is a minimum: the block is read in the first loop in which at least that many milliseconds have passed. If a loop takes 300 ms, a tag with scan=1000 is read about every 1200 ms, and a scan shorter than the loop behaves like 0. The Check button shows the blocks and how often each one is read.

          Timing: serial port and TCP

          The daemon makes one request at a time. Each request takes:

          • the wait before the request (idletime): on serial lines 3.5 characters as Modbus RTU requires (4 ms at 9600 baud, at least 2 ms); with TCP, 0;
          • the transmission: at 9600 baud each byte takes about 1 ms (reading 8 registers: about 30 ms);
          • the slave response: typically 5 to 20 ms.

          That is why grouping helps so much on serial lines: 8 contiguous registers in one request take about 40 ms; in 8 requests, about 300. The scan does not speed up the communication: it shares out the time, leaving the line free for the values that are read in every loop. Writes also use the line.

          Settings of the .mkmodbus:

          SettingDefaultPurpose
          idletime=serial: 3.5 characters; TCP: 0ms before each request. For slow devices or serial/Ethernet converters that need it (idletime=41 is the wait of the previous versions at 9600 baud).
          cycletime=50Minimum duration of a loop in ms: the daemon does not read more often than this (it does not overload the PLC or the CPU). cycletime=0: no pause.

          9.7Address in the PLC

          The tag monitor shows, in the Address column, where each tag is in the PLC: %MW0.0 (Modbus) or DB10.DBX0.1 (Siemens). The daemon writes it into the .tagmap (plcaddr=); a structure shows the address of its first member. The monitor filter also searches by address. The daemons must be regenerated for the .tagmap files to carry it.

          9.8Sorting tables

          In the tag editor (the tables of tags and structure members) a click on a column header sorts by it; another click reverses the order.

          • The order is numeric or natural (Motor2 before Motor10) and empty cells go last. Combos and check boxes sort by their value.
          • Sorting only changes the view: the order of the tags in the files does not change, unless Up or Down is used.

          10Structures and arrays

          10.1Arrays

          With Count > 1 the variable is an array: Temp[0], Temp[1], ... with consecutive addresses, or every Stride registers (bytes in S7). In bit arrays the stride is in bits.

          tag name=Temp   address=40100   type=real count=10            # Temp[0..9]: 40100, 40102, ...
tag name=Alarm  address=40200.0 type=bool count=32            # 32 bits: 40200.0 ... 40201.15
tag name=Level  address=40300   type=int  count=4 stride=10   # 40300, 40310, 40320, 40330

          10.2Structures

          A structure is a compound type, like the UDTs of PLCs. It is defined once (Structures tab) and used as the type of one or more variables. Each member has a Position relative to the start (registers in Modbus, bytes in S7; with .bit for a bool). Without a position, the member follows the previous one (consecutive bools take the next bit).

          struct name=Motor desc="Pump motor"
member name=Run       at=0.0 type=bool rw=1
member name=Fault     type=bool              # 0.1 (follows)
member name=Speed     at=2   type=real rw=1
member name=Current   type=int scale=0.1     # 4
member name=Alarm     type=bool count=3      # 5.0, 5.1, 5.2
end
tag name=Pump1 address=40500 type=Motor
tag name=Pumps address=40600 type=Motor count=4 stride=10    # one motor every 10 registers

          In the pvserver:

          float v = PLC1.getReal(PLC1_Pump1.Speed);
PLC1.setBool(PLC1_Pumps[2].Run, 1);
for(int i=0; i<PLC1_Pumps_COUNT; i++)
  pvPrintf(p, Table, ...);   // walk through the array

          Positions do not have to be consecutive (there can be gaps) and structures can be used in several variables or in arrays. Each structure is read in a single block if its members are close together.

          10.3Structures shared between daemons

          If a project has several daemons (for example two Modbus PLCs and a Siemens one) with the same kind of equipment, the structure Motor is defined only once: in the Structures tab of the tag editor, tick Shared with the other daemons of the project. The structure is stored in <project>.mkstruct and each daemon file gets a line structs=<project>.mkstruct; if the daemon has its own structure with the same name, that one takes priority.

          # pvs.mkstruct
struct name=Motor desc="Pump motor"
member name=Marcha    type=bool rw=1
member name=Falla     type=bool
member name=Velocidad type=real rw=1
end

          With the At (position) column empty, the same structure works for any protocol (Modbus and Siemens): the members follow one another.

          11Siemens S7

          The SiemensTCP daemon (Daemon > Siemens TCP) works like the Modbus one. The PLCs are declared with slave=:

          slave=0 adr=192.168.1.101 type=S7_300 fetch_write=0 function=-1 rack_slot=-1

tag name=Flow   address=DB10.DBD8 type=real
tag name=Input  address=I0.1
tag name=Output address=QB2 rw=1
          AddressDefault type
          DB10.DBX4.3, M10.3, E0.1/I0.1, A0.1/Q0.1bool
          DB10.DBB4, MB10, EB0/IB0, AB2/QB2byte

          12Using the tags in the pvserver

          12.1Preparing the project

          1. In pvapp.h: #include "PLC1.h" (the .h generated by pvdevelop).
          2. In main.cpp, once: rlModbusClient PLC1(PLC1_MAILBOX, PLC1_SHARED_MEMORY, PLC1_SHARED_MEMORY_SIZE);
            (Siemens: rlSiemensTCPClient; same arguments).
          3. In each maskN_slots.h that uses it: extern rlModbusClient PLC1;
          4. RLlib > Uncomment rllib adds the libraries to the .pro.
          5. The daemon must be running (on Windows from a console, or as a service).

          12.2Functions

          FunctionReturns / does
          getBool(tag)0 or 1
          getInt(tag) / getUInt(tag)Integer, without scale
          getReal(tag)Value with the scale of the tag (any type)
          quality(tag)1 = read correctly; 0 = communication error
          setBool(tag, v), setInt(tag, v), setReal(tag, v)Writes (the tag must be RW). setReal applies the scale in reverse.
          rlTagFind(PLC1_tags, PLC1_TAG_COUNT, "Pump1.Speed")Finds a tag by name (returns a pointer or NULL)

          12.3The PLC1_ prefix and tags without prefix

          The variables are called PLC1_<name> (the daemon name and an underscore) for two reasons: in each mask the widgets are C++ names too (Temp, Motor1, ...) and often a variable and a widget have the same name; and a project can have several daemons with tags of the same name (PLC1_Run, PLC2_Run).

          To write only the name, the .h has the same tags in namespace tags_PLC1:

          using namespace tags_PLC1;               // in the mask (maskN_slots.h)

float t = PLC1.getReal(Temp);
PLC1.setBool(Pumps[2].Run, 1);
for(int i=0; i<Temp_COUNT; i++) ...

          If a name matches a widget of that mask, the compiler complains (reference to 'Temp' is ambiguous); then the full form is used, PLC1_Temp or tags_PLC1::Temp. tags_PLC1::Temp can also be used without the using.

          12.4Complete example

          static int slotNullEvent(PARAM *p, DATA *d)
{
  if(PLC1.quality(PLC1_Temp) == 0)
  {
    pvSetText(p, LabelTemp, "no communication");
    return 0;
  }
  pvPrintf(p, LabelTemp, "%.1f °C", PLC1.getReal(PLC1_Temp));
  pvSetChecked(p, CheckRun, PLC1.getBool(PLC1_Pump1.Run));
  return 0;
}

static int slotButtonEvent(PARAM *p, int id, DATA *d)
{
  if(id == ButtonStart) PLC1.setBool(PLC1_Pump1.Run, 1);
  if(id == ButtonStop)  PLC1.setBool(PLC1_Pump1.Run, 0);

static int slotSliderEvent(PARAM *p, int id, DATA *d, int val)

  if(id == SliderSpeed) PLC1.setReal(PLC1_Pump1.Speed, val);
  return 0;
}

          13Widget actions and animations (Tags...)

          A button can write a tag, a label can show a tag's value and a drawing can change colour without writing a single line of code: you configure it in the Designer and pvdevelop generates the code. Everything below applies to C/C++ pvservers (not Lua) and works the same on Windows, Linux.

          13.1Opening the dialog

          1. In the Designer, Alt+click on the widget (or right click > Properties): the Properties dialog opens.
          2. Button Tags.... If the widget already has bindings the button shows a ✓ mark and a summary.
          3. The dialog Action and animation of <widget> has two tabs: Action (what happens when the widget is used) and Animation (how it looks depending on tags).
          The tag list comes from the daemons' .tagmap files. If it is empty, the dialog says There are no tags: compile the daemon first (Daemon > Modbus / Siemens TCP, Compile button) so that it is generated. A tag is chosen as Source:name (for example PLC1:Motores[0].Marcha); you can type part of the name in the box to filter.

          13.2Action tab

          Group When the widget is used: three rows, On click, On press and On release. In each one choose the action, the tag and, depending on the action, a value or a screen.

          ActionWhat it does
          NoneDoes nothing.
          Write valueWrites the fixed value to the tag (write:PLC1:Bomba=1).
          Toggle (bool)Inverts the tag (toggle:PLC1:Bomba).
          Add / SubtractAdds or subtracts the value to/from the tag (for + and − buttons); respects the minimum and maximum limits.
          Go to screenSwitches to the given mask (goto:3).
          Back / HomeReturns to the previous screen or to the first one.

          The Momentary button button fills the three rows to write 1 on press and 0 on release (for example "run while held down").

          Options

          FieldWhat it is for
          Write the input toFor LineEdit (the typed number, on Enter), Slider, Dial, SpinBox (their value) and CheckBox (1 or 0): the tag that receives the value.
          Limits (add, subtract, input)Minimum and maximum; a value out of range is clipped or rejected.
          Confirm first (click)Text of a Yes/No question (for example Start motor 1?). Empty = no confirmation.
          Only ifCondition on another tag (==, !=, >, >=, <, <=) and the message shown when it is not met (an interlock: "do not start with the gate open").
          The actions login, logout, users, ack, recipes, automation, faceplate and close, and the texts @user and @automation, belong to the full version of PV Suite. If a project made with that version contains them, they are kept in the project but do nothing here, and pvdevelop warns when generating.

          13.3Animation tab

          FieldEffect
          TextShows a tag in the widget. printf format (%.1f C, %d, %.2f bar) or texts per value separated by | (Stopped|Running|Fault: 0, 1, 2).
          ValueFor ProgressBar, Slider, Dial, SpinBox, LCDNumber, CheckBox and RadioButton: their value follows the tag.
          ColorTable value=color separated by ;: 0=#808080;1=#00C000;>80=#FF0000;else=. Accepts > >= < <= != and else (empty colour = the original one). Applied to the Background or the Text.
          BlinkThe widget blinks while the tag is 1 (an alarm).
          VisibleShown only when the tag is non-zero; invert shows it when it is 0.
          Grey if the data is badIf the tag could not be read or the daemon is not running (quality 0), the widget is shown grey.
          Image by valueFor image widgets: one file per value (stopped.png|running.png|fault.png); the last one is used for higher values.
          Animate whileWhile the tag is not 0 pvbrowser shows the frames one after another (pump1.png|pump2.png|pump3.png) with the period given in ms. An animated .gif animates by itself.

          Images are searched in the project folder; to include them inside the executable see chapter 14.

          13.4What pvdevelop generates

          When the mask is saved, pvdevelop writes maskN_pvb.h (do not edit it: it is regenerated), includes it in maskN.cpp and adds a line pvbActions(...) / pvbAnimate(...) in each slot of maskN_slots.h. The bindings are stored in the header of the file, one line per widget:

          //pvb: btnBomba press=write:PLC1:Bomba=1 release=write:PLC1:Bomba=0 color=PLC1:Bomba colors="0=#808080;1=#00C000" level=1
//pvb: btnTorre click=toggle:PLC1:FlagTWR confirm="Change tower control?" cond="PLC1:Brillo < 50" condmsg="Brightness too high"
//pvb: btnMas   click=add:PLC1:Motores[0].Velocidad=5 max=100
//pvb: lblEstado text=PLC1:Motores[0].Marcha fmt="Stopped|Running"
//pvb: lblTemp  text=PLC1:Temp fmt="%.1f C" quality=0 blink=PLC1:AlarmaTemp
          KeyMeaning
          click press releaseAction: write:TAG=V, toggle:TAG, add:TAG=5, sub:TAG=5, goto:3, back, home, faceplate:Block:TAG, close, login, logout, users, ack:all, recipes:Type, automation:pause|resume
          enter min maxTag that receives the input, and its limits
          confirm cond condmsgPrevious question and condition
          text fmt valueText and value
          color colors colorpartColour by value; colorpart=bg|fg
          blink visible qualityBlinking, visibility (!TAG = inverted), grey if the data is bad
          image images anim frames periodImages and animation

          A tag written as PLC1:name is translated in the code to PLC1_name with the PLC1 client of main.cpp; you do not need to touch it. To avoid loading the network, pvbrowser only receives what changed.

          13.5Your own code

          The widget's slot is still available. Your own code goes before or after the pvbActions line; the code before it can prevent the action (by returning a value), the code after it always runs. The bindings can be edited by hand in the //pvb: header of maskN_pvb.h, but the dialog is the normal way.

          13.6Step-by-step example: run button with indicator

          1. Compile the daemon (PLC1) to get its tags.
          2. In the Designer insert a PushButton btnBomba and a label lblBomba.
          3. btnBomba > Properties > Tags...: Momentary button with tag PLC1:Bomba; Minimum level 1.
          4. lblBomba > Tags... > Animation: Text PLC1:Bomba with format Stopped|Running; Color 0=#808080;1=#00C000.
          5. Ctrl+S, Ctrl+M (compile) and Ctrl+T (run). Open pvbrowser with Ctrl+P.
          A pvbrowser older than this version ignores the new commands (alarm banner, image animation) without an error; everything else works.

          13.7Integer bits and conditions

          A screen can use a bit of an integer as if it were a tag: PLC1:Estado.3 is bit 3 of PLC1:Estado. It works in texts, colors, visible, blinking, animations and in the toggle: and write: actions.

          • Read: integers of type byte, int, uint, dint and udint. Write: only 8 and 16 bits. In Modbus it is written with Mask Write; in Siemens, in the byte address + size-1-bit/8 (bit 10 of DBW300 is DBX300.2).
          • pvdevelop reports in the ATENCION block of maskN_pvb.h if the bit is of a real or a bool, is out of range, or if a 32-bit bit is to be written.
          • In Modbus with byte order BADC or DCBA, the bit of a register is written as a bit of the register, not of the reordered value.

          Conditions

          Wherever the screen asks for a condition (Animate while, Visible, Blink and the only if of actions) you can write:

          ConditionTrue when
          PLC1:Bombathe tag is true (non-zero)
          !PLC1:Bombathe tag is false
          PLC1:Estado == 2comparison with a value: ==, !=, >=, <=, >, < (a single = counts as ==)
          PLC1:Estado.3bit 3 of the integer is 1

          14Embedded images

          Normally images are distributed as files next to the pvserver and pvbrowser downloads them. With embedded images they are stored inside the executable: you do not need to copy the image folder to the production PC and nobody can change or delete them.

          14.1How to use them

          • One image: widget Properties > Embed image checkbox.
          • All together: Action > Project resources.... The table has the columns Embed, File, Size (sortable) and Used in. The buttons Check used ones (those used by the masks), All and None help; Save stores the list.
          • When you pick an image from any folder in the properties, pvdevelop offers to copy it to the project's Image/ folder.

          The list is stored in <project>.pvres (one file per line). At every build pvdevelop generates pvresources.cpp with the data (and adds it to the .pro) only if something changed. At run time the pvserver sends the embedded image to pvbrowser once per connection, as a temporary file, and pvbrowser deletes it on exit.

          # Files embedded in the pvserver (pvdevelop: Action > Project resources)
imagenes/off.png
imagenes/on.png
imagenes/luz.gif

          14.2Image animation

          The animation is done by pvbrowser (no traffic while it animates). It is configured in Tags... > Animation > Animate while (see 13.3) or from code:

          pvSetImageAnimation(p, Bomba, "pump1.png,pump2.png,pump3.png", 300);   // frames and period in ms

          Animated .gif files play by themselves. This applies only to C/C++ pvservers.
